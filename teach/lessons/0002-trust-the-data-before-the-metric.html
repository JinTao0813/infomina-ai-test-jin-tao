Provenance and schema

The brief permits any public spatio-temporal dataset. TSMC 2014 has the required user, venue, category, coordinate, and timestamp fields across NYC and Tokyo. The author's readme states 227,428 and 573,703 check-ins. Local SHA-256 hashes and line counts identify this exact dataset version.

The loader uses headerless Latin-1 TSV with eight explicit names and dtypes. Explicitness prevents inferred IDs becoming numbers, silent encoding failure, or schema drift passing unnoticed.

Quality gates

1StructureCount seven tabs per row; reject malformed field counts.
2Required fieldsReject null and blank identifiers, labels, coordinates, offsets, or timestamps.
3CoordinatesLatitude ∈ [−90, 90], longitude ∈ [−180, 180]. This checks validity, not city membership.
4TimeParse exact source format as timezone-aware UTC; convert to named city timezone.
5Quality reportDuplicates, activity, home events, offset anomalies, and venue metadata conflicts.

Three decisions interviewers probe

Composite identity

User IDs restart in each file: all 1,083 NYC IDs appear in Tokyo's numeric ID space. Bare user_id would merge different people. The analytical key is (city, user_id).

Exact deduplication

Remove rows identical across all eight source columns. Otherwise an accidental replay receives extra count and therefore extra probability mass. Do not deduplicate only on user–venue: legitimate repeat visits are the behavior being measured.

Named timezones

UTC is stable storage; local calendar context is derived with America/New_York and Asia/Tokyo. Named IANA zones encode daylight-saving transitions; fixed offsets do not. Supplied offsets are retained as a quality signal, not used as truth, because 456 NYC and 27 Tokyo rows are inconsistent.

Subtle implementation detail: derive context within each city frame before concatenating. Different local timezone dtypes can otherwise collapse to an object-like representation.

Private homes and metadata conflicts

Home (private) is retained because routine is analytically meaningful, but coordinates and trajectories are never reported. A later exclusion sensitivity test checks whether it drives conclusions. Venue/category and venue/coordinate conflicts are reported rather than “fixed” with an arbitrary canonical record. Venue entropy only needs IDs; category entropy uses each event's recorded category_id.

“The loader fails closed on structural invalidity, reports non-fatal semantic anomalies, removes only exact event duplicates, protects cross-city identity, and derives calendar context from named city timezones.”

Retrieve

Why not deduplicate on user and venue?
That would erase legitimate repeat behavior and change the empirical probability distribution the entropy metric is meant to summarize.
Where did the “expected” counts come from?
Raw rows come from the author's readme and line counts; duplicates and unique users/venues/category labels come from profiling the exact downloaded files after the documented deduplication rule.

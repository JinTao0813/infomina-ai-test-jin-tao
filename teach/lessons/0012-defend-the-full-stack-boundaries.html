There are two runtime paths

AStatic analysisExecuted notebook → offline safe exporter → committed JSON/images → Next.js analysis renderer. No FastAPI or raw check-ins required at runtime.
BInteractive prototypeBrowser controls → JSON request → local FastAPI → deterministic in-memory ranker over committed safe fixtures → explained results.

This split avoids turning the notebook into a second manually copied report while keeping the analysis readable if the API is down. The notebook remains authoritative; the site is a deterministic presentation artifact tied to its source SHA-256.

Exporter defense

scripts/export_notebook_presentation.py accepts only notebook format 4 and a bounded set of cells/output types. It rejects execution errors, scripts, iframes, event handlers, unsupported media, and charts without alt text/captions. It converts HTML tables into structured text, extracts fingerprinted images, copies referenced static assets, and records the notebook hash. Validation re-exports in isolation and compares both artifact and assets.

“The website is generated from the executed notebook rather than separately authored, so there is one analytical source of truth. Export does not execute code. Build-time freshness checks tie the presentation to the exact notebook bytes and reject unsafe or unsupported output.”

Candidate defense

The sixteen candidate records are data-derived aggregates, not synthetic venues and not current recommendations. Offline generation:

  1. loads actual NYC/Tokyo source records;
  2. excludes home/private/residential/workplace categories;
  3. requires at least 30 historical check-ins and 15 distinct visitors;
  4. selects eight per city across the eligible popularity range deterministically;
  5. rounds support to groups of five;
  6. replaces absent source names with honest city/category/candidate-number pseudonyms;
  7. drops source venue/user IDs, coordinates, timestamps, and trajectories.

The four profiles are different: they are entirely synthetic fixed examples anchored to aggregate ranges. Saying “all fixtures are synthetic” is therefore inaccurate.

Live service boundary

FastAPI loads only committed profile and candidate JSON at process start. Pydantic forbids unknown fixture fields and constrains ranges. Requests constrain context/mode enums and limits 1–12; unknown profiles return 404. Development CORS allows documented local frontend origins. The frontend does not duplicate ranking logic—it sends controls, then renders returned reasons and components.

Why build more than the brief required?

The notebook already satisfied code + methodology/findings. The companion site improves reviewer access, and the prototype demonstrates technical and creative capacity by making the product hypothesis falsifiable and inspectable. Scope remains bounded: no training, database, auth, map, live API, persistence, deployment infrastructure, or effectiveness claim.

Residual privacy and truth limits: aggregation and pseudonymization reduce exposure; they do not constitute a formal privacy proof. Support thresholds are pragmatic, not differential privacy. Historical candidates may be closed or sensitive in ways the old category cannot reveal. Production use still needs review and current data.

What happens when FastAPI is unavailable?
The generated analysis route still renders from committed JSON/assets. Discovery Mode shows a recoverable API error because only its interactive ranking path requires FastAPI.
Why are pseudonymous candidates preferable to invented proper names?
The source contains no venue names. City/category/number labels preserve provenance without fabricating identity or exposing source venue IDs.
Does a 30-check-in/15-visitor threshold guarantee anonymity?
No. It is a pragmatic minimization rule alongside field removal and rounding, not a formal privacy guarantee such as differential privacy.
